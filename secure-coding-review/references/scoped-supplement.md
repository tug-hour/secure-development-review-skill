# 独立補完の依頼と統合

主担当がSKILL.mdの適用条件を満たす場合だけ使う。補完担当は下記の調査を担当し、追加委任や主レビュー全体の再実行は行わない。

## 主担当から渡す入力

- 対象の場所・版、依頼範囲と影響する呼出し側/設定/利用例、既知の利用条件・保護要求。
- 読取り/実行/通信等の権限と制約、利用可能な元コード・設計・設定と本スキルの参照資料の場所。
- 下記の補完担当の仕事。モデル・Effort等に指定があれば環境の共通ルールと合わせて守る。

補完担当は新規の独立コンテキストで起動し、上記の必要入力だけを渡す。主報告・期待所見・主担当が問題と疑う経路・他方式の結果を含む会話履歴を引き継がせない。ただし依頼者が示した対象範囲や判断に必要な利用契約・設定を隠さない。元コードや版/行番号付きの取得結果は共有できるが、主担当の選択的な要約だけを唯一の入力にしない。補完担当が元の対象を検索できる状態を保つ。

依頼文は必要入力と担当の仕事だけの平文として確認可能にし、検証時はその文面を残す。進行確認は起動で得た担当IDへの連絡・完了通知を使い、他タスクの報告を返す担当一覧を取得しない。補完担当にも同じ制約を渡す。これは情報分離の運用条件であり、実行基盤による強制を保証しない。

## 補完担当の仕事

失敗後に別実装・別設定・次の反復で継続して成功を返す構造と、失敗値が通常の選択・設定として後続で使われる構造の候補を挙げ、その根拠を再利用して関連経路を調べる。既存の検索・読取り・許可された解析手段を使い、関数名や特定OSSの既知所見を前提にしない。新しい解析基盤や依存の導入を前提にせず、検索式と候補選択にもモデル判断が残ることを認識する。

関数・設定・利用例をつなぎ、失敗値、代替先、後続の成功と必要な保護を対応させる。候補を欠陥と仮定せず、同等の保護を保つ代替や意図した旧設定の受理と区別する。不明な要求を創作せず、成立条件・既存防御・影響・対応又は不足証拠を示す。原典の具体条件が結論を左右するときは[参照案内](criteria.md)から必要箇所を使い、前提・例外・数値・要求の強さを保持する。

候補の箇所と未処理の問いを短く保持し、同じ分岐/経路は共通根拠を使う。別の原因・成立条件・対策は一つの所見で閉じない。取得済みで足りるコードは再取得せず、前提変更・切詰め・重要な証拠不足だけ必要部分を補う。必要な呼出し側や後続処理を省略して速くしない。全体の再レビュー・全ガイド判定・専用台帳・件数目標は要求しない。

候補が、所見・保護維持の根拠・理由付き範囲外・必要証拠と取得不能理由を持つ未確認のいずれかとなり、取得可能な重要証拠への調査が終わったら返す。候補ゼロでも検索/確認範囲と扱えない構造を示す。候補数や短時間だけを理由に黙って除外しない。制約で止まる場合は未処理の範囲・理由・必要な証拠を示し、補完完了/安全としない。

重要候補は「箇所と根拠／失敗前後の保護の変化／成立条件／判断・対応又は不足」を一つの短い記載で返す。仕様で許される動作であることと、利用側の保護要求を満たすことは別に判断する。要求が不明なら創作せず、成立条件付きリスクか未確認として区別する。抽出報告と調査報告を二重に作らない。主担当の所見を受け取っていないため「新規」の判定は主担当が行う。

## 主担当の統合

補完担当の調査・判断が終わるまで主所見を渡さない。返却後は所見保持のために共有し、SKILL.md「調査範囲と報告本文」に従って主の報告本文を直接編集する。

- 新しい有効所見・重要な未確認は、補完の具体的な記述を本文へ取り込む。掲載前にもう一度一般論へ要約しない。
- 同じ原因・経路・成立条件の所見だけ統合し、追加の根拠・条件・影響・対応を残す。異なる問題は分ける。
- 矛盾は該当する根拠と前提だけを確認する。誤り・非該当は理由付きで訂正し、解消できないものは不足証拠付きの未確認にする。
- 本文と受領所見を照合し、既存・追加の有効内容が残ったことを確認する。主の調査範囲の完遂も別に確認し、補完担当の範囲外の観点まで補完済みとしない。

候補全量の連結、別台帳、統合専用担当、毎回の検証用記録一式は不要。未完なら理由と範囲を示す。
